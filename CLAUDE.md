# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
yarn dev              # dev server at http://localhost:3000
yarn build            # tsc + vite build to /build
yarn lint             # ESLint
yarn format           # Prettier write
yarn format:check     # Prettier check (used in CI)
yarn test             # Vitest watch mode
yarn test:run         # Vitest single run (used in CI)
yarn test:coverage    # Vitest with v8 coverage, outputs coverage/coverage-summary.json
yarn test:e2e         # Playwright smoke tests against `vite preview` of /build (run yarn build first)
```

**Run a single test file:**

```bash
yarn test src/tests/CommonHooks.test.tsx
```

## Architecture

### Repo layout

The repo has two top-level concerns:

- `src/` (plus `package.json`, `vite.config.ts`, etc. at the repo root) - the React/Vite app (all frontend work happens here)
- `scripts/` - Python scripts called by GitHub Actions to regenerate `src/data/*.json`

### Routing

`src/main.tsx` uses `createHashRouter` (required for GitHub Pages). Routes:

- `/` - HomeContent
- `/experience` - ExperienceContent
- `/hobbies` - HobbyContent
- `/blog` and `/blog/:slug` - BlogContent and BlogPost
- `/vinopilot` - VinopilotContent (main project, linked from the home intro)
- `/asher-zone` - AsherZoneContent (Easter egg, floating particle physics)

### Component model

`Home.tsx` is the persistent shell: it owns the MUI drawer (a modal `temporary` drawer below the `sm` breakpoint, a collapsible permanent rail from `sm` up), AppBar, theme provider, and keyboard shortcuts. Page components are rendered inside it as route children. All hooks live in `src/hooks/CommonHooks.tsx` - this is the single file for `useAppTheme`, `useYouTubeMusic`, `useKeyboardShortcuts`, `usePageTitle`, and `useGitHubRepo`.

### Theme

`useAppTheme()` manages light/dark mode. State persists to `localStorage` under the key `theme`. With nothing saved it follows the device's `prefers-color-scheme` (live, including changes while the page is open) and falls back to dark; once the user toggles, the saved choice wins. The full MUI theme object (palette, typography, component overrides) is built inside this hook - there is no separate theme file. Colours follow Material You (M3): the light/dark role palettes in `src/constants/materialSchemes.ts` are generated from `THEME_SEED` with `@material/material-color-utilities` (a devDependency, kept out of the bundle) and mapped onto MUI's palette in the hook. To change the seed, update `THEME_SEED` and regenerate the values; `materialSchemes.test.ts` fails until they match.

### Static data pipeline

Two JSON files in `src/data/` are auto-generated by GitHub Actions and committed to the repo. They are imported directly at build time - there are no runtime fetches for this data.

| File         | Generator                                   | Schedule             | Consumer              |
| ------------ | ------------------------------------------- | -------------------- | --------------------- |
| `pulse.json` | `scripts/summarize.py` via `pulse.yml`      | Every 3 days         | `GitHubPulse.tsx`     |
| `stats.json` | `scripts/generate_stats.py` via `stats.yml` | Weekly Mon 02:00 UTC | `SiteStatsWidget.tsx` |

`pulse.json` contains an AI-generated summary of recent commits (Anthropic API, `claude-haiku-5-5`, authenticated with Workload Identity Federation: the script exchanges the GitHub Actions OIDC token using the `ANTHROPIC_FEDERATION_RULE_ID`, `ANTHROPIC_ORGANIZATION_ID`, `ANTHROPIC_SERVICE_ACCOUNT_ID` and optional `ANTHROPIC_WORKSPACE_ID` repo variables or secrets; `ANTHROPIC_API_KEY` works as a local fallback; on failure the previous summary is kept). `stats.json` contains Vitest coverage percentages and Lighthouse scores. If these files need regenerating locally, run the Python scripts directly - they have no dependencies beyond the standard library and `requests`.

### Standard.site publishing

`scripts/publish_standard_site.py`, run by `standard-site.yml` whenever `src/data/posts/**` or the script itself changes, publishes [Standard.site](https://standard.site) lexicon records (`site.standard.publication`, `site.standard.document` per post) to the `pds.karanshukla.ca` PDS so posts surface in Standard.site readers like standard-reader.app. It's idempotent: `src/data/standardSiteRecords.json` maps the publication and each post slug to its record AT-URI/CID/content-hash, so the publication record is only re-pushed (via `putRecord`) when `PUBLICATION_NAME`/`PUBLICATION_DESCRIPTION` actually change, unchanged posts are skipped, and removed posts have their records deleted. The first successful run also writes `public/.well-known/site.standard.publication` (the domain verification file, containing the publication record's AT-URI) - that file must be committed once created and never hand-edited. Requires the `PDS_APP_PASSWORD` repo secret, and reads the login identifier from the `PDS_IDENTIFIER` secret (falls back to the `karanshukla.ca` handle if unset) - prefer setting `PDS_IDENTIFIER` to the account's DID so the workflow survives a future handle change. The script does not touch the app's UI or routing.

### Prerendered blog pages

`prerenderBlogPages.ts` is a Vite build plugin that writes `build/blog/<slug>.html` for every post (GitHub Pages serves it at `/blog/<slug>`), plus a `404.html` copy of `index.html`. Each page is the normal SPA shell with a per-post `<title>`, description, canonical, Open Graph/Twitter tags (image: `public/og-image.jpg`) and the `<link rel="site.standard.document">` verification tag from `standardSiteRecords.json`, so crawlers and standard.site can read them without JS. On load, `moveUrlPathIntoHashRoute()` in `main.tsx` rewrites `/blog/<slug>` (or any other hash-free path) to `/#/blog/<slug>` so the hash router renders it. Document records point at `/blog/<slug>` for the same reason.

### YouTube Music recently played

`NowPlayingWidget` shows the latest song from YouTube Music history. YouTube Music has no public API, so `scripts/fetch_youtube_music.py` (run hourly at :23 by `now-playing.yml`, kept infrequent to stay clear of YouTube Music rate limits) reads it with the unofficial `ytmusicapi` library, authenticated with the `YTMUSIC_OAUTH_TOKEN` (contents of the `oauth.json` from `ytmusicapi oauth`), `YTMUSIC_CLIENT_ID` and `YTMUSIC_CLIENT_SECRET` secrets. The Google OAuth client must be a "TVs and Limited Input devices" client, and its consent screen must be published ("In production") or Google expires the refresh token after 7 days. When the track changes, the workflow force-pushes `now-playing.json` as a single orphan commit to the `now-playing` branch, so `main` is untouched and nothing redeploys. `useYouTubeMusic()` in `CommonHooks.tsx` polls that file on raw.githubusercontent.com every 5 minutes. YouTube history only gives a day bucket ("today", "yesterday"), so the file also records `firstSeenAt`; tracks first seen in the last hour count as "just played". Genre tags are looked up once per track from ListenBrainz's metadata lookup in the script. A failed history read exits 1 so an expired token shows up as a failed run; the widget keeps showing the last published track. Thumbnails come from `lh3.googleusercontent.com` (songs) or `i.ytimg.com` (videos), both in the CSP `img-src`.

### GitHub repo cards

`useGitHubRepo(owner, repo)` fetches live star/fork counts and language from the GitHub API at runtime in the browser. No auth token - uses the public rate limit.

### AsherZone

`src/modules/AsherZone.ts` is a self-contained canvas/physics module (~370 lines). It is intentionally excluded from test coverage. Do not add it to the coverage include list.

### Build output

Vite outputs to `/build` (not `/dist`). The `CNAME` file is written by the deploy workflow, not committed to the repo.

## Code style

Prettier config: single quotes, semi, 2-space indent, 100-char print width, trailing commas. ESLint uses the modern flat config format (`eslint.config.js`). TypeScript strict mode is on with `noUnusedLocals` and `noUnusedParameters`.

### Comments

Don't add comments above functions or inline unless the WHY is genuinely non-obvious (a hidden constraint, a subtle invariant, a workaround for a specific bug). Well-named identifiers should make the WHAT self-evident. Before reaching for a comment, check whether the explanation can instead be expressed through abstraction or encapsulation — e.g. logic embedded in a component should move to a self-commenting, domain-named hook or helper rather than being explained in a comment. Favor human-readable, domain-driven names and logical flow over prose explanations, while keeping code legible to agents working in this repo.

## Tests

Test files live in `src/tests/` and mirror component names. `AsherZone.ts` and `AsherZoneContent.tsx` are excluded from coverage. The setup file (`src/tests/setupTests.ts`) only polyfills `scrollIntoView` - keep it minimal.

Playwright smoke tests live in `e2e/` and run against the built site, so the CSP meta tag in `index.html` is enforced. Third-party requests (the now-playing file, album art, GitHub) are mocked with `page.route`; any console error, including a CSP violation, fails the test.
